# Промпт для будущих чатов: copy-paste-ready файлы

Скопируй блок ниже в начало нового чата, чтобы получать файлы в формате «нажал Copy → вставил в файл». Без правок, без вычищения вложенных обёрток.

---

## Промпт

При написании файлов (`.md`, `.py`, `.json`, `.yaml`, `.txt`, `.env` и т.д.) придерживайся следующих правил.

### 1. Один файл — один fenced-блок

Весь контент файла оборачивай в **один** code-блок с указанием языка. Вне блока — только путь к файлу и краткое описание.

### 2. Внешний fence длиннее внутренних

Если внутри файла есть тройные обратные кавычки (например, `.md` с примерами кода):

- **Внешний блок — 4 обратные кавычки**
- **Внутри — обычные 3 обратные кавычки** для примеров кода

Если в файле нет тройных обратных кавычек — использовать стандартные 3.

### 3. Путь к файлу — строкой над блоком

Формат:

📄 path/to/file.ext

Пример правильного оформления: сначала строка с эмодзи и путём, затем пустая строка, затем fenced-блок с кодом.

### 4. Внутри блока — только чистый контент файла

- Без фраз «вот ваш файл», «не забудьте», «здесь можно поменять»
- Без двойных обёрток типа «markdown-блок внутри markdown-блока»
- Все пояснения — **до** или **после** блока

### 5. После блока — не больше 5 строк описания

Что изменилось, зачем, на что обратить внимание. Не дублировать содержимое файла.

### 6. Большой файл (>500 строк)

- Предупредить
- Спросить: отдать целиком или разбить на части
- Если целиком — использовать внешний fence из 4 обратных кавычек
- Если частями — каждая часть в отдельном блоке с пометкой «часть N/M»

### 7. Правка существующего файла

- Показать **весь** файл после правок (не diff, не фрагмент)
- В описании после блока перечислить только изменённые места
- Никогда не писать «... остальное без изменений ...»

### 8. Несколько файлов — несколько блоков

Два файла = два отдельных блока. Даже если короткие. Разделять `---` или заголовком с путём к файлу.

### 9. Если просят «весь проект»

- Один блок на файл
- Порядок: от «входных» (`config`, `models`, `requirements.txt`) к «выходным» (`main.py`, `tests`)
- Между блоками — заголовки с путями

### 10. Язык fence — корректный

| Расширение | Язык fence |
|-----------|-----------|
| `.md` | `markdown` |
| `.py` | `python` |
| `.json` | `json` |
| `.yaml` / `.yml` | `yaml` |
| `.env`, `.gitignore`, `.txt` | `text` |
| нет расширения | (без языка) |

### 11. Если инструмент не поддерживает 4-backtick outer fence

Fallback: использовать обычный markdown-блок с тремя обратными кавычками снаружи и **indented-блоки (4 пробела)** для вложенного кода. Пример вложенного кода в этом случае оформляется так:

    bash
    pip install -r requirements.txt

Такой подход гарантированно работает во всех редакторах и парсерах, потому что внутри внешнего блока вообще нет символов обратной кавычки, которые могли бы его закрыть.

**Важно:** никогда не пиши символы обратной кавычки прямо в тексте описания (например, «использовать тройные обратные кавычки») без необходимости. Если нужно упомянуть их, пиши словами: «три обратные кавычки», «fence из четырёх обратных кавычек».

---

## Цель

Пользователь нажимает **Copy** на блоке → вставляет в файл → сохраняет. Без правок, без вычищения вложенных обёрток, без ручной сборки из фрагментов.
