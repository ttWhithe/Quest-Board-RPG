## Важные архитектурные решения (не ломать!)
1. **Модалка вместо страницы:** Создание квеста вызывается через модалку на `/board`. Отдельного роута `/quests/new` нет.
2. **TypeScript strict:** Включен `verbatimModuleSyntax`. Типы импортируются строго через `import type { ... }`.
3. **Pre-commit:** Если pre-commit изменил файлы (end-of-file, line endings), просто сделай `git add .` и повтори коммит.
4. **Сборка:** Dev-сервер Vite не проверяет типы. Перед коммитом всегда проверяй вкладку Problems в VS Code или запускай `npm run build` локально.

## Уроки прошлых дней (чтобы не повторять ошибки)
1. **TS1484:** При импорте интерфейсов (например, `Quest`, `QuestFilters`) обязательно использовать `import type`.
2. **TS6133:** Удалять неиспользуемые импорты (например, `useTranslation` или `Link`), иначе CI упадет.
3. **Форматирование:** Полные файлы от ИИ лучше вставлять целиком (Ctrl+A -> Ctrl+V), чтобы не ломались скобки.
4. **Vite 8 + Vitest:** `vite.config.ts` и `vitest.config.ts` должны быть разделены (через `mergeConfig`), иначе TS ругается на несовместимость типов плагинов (Rolldown vs Rollup).

## Правила работы (ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ)

**Общие правила и формат ответов:**
1. Отвечай по-русски.
2. **Никаких догадок:** Если нужен контекст существующих файлов — прямо проси их прислать. Если упал CI — проси лог ошибки, не гадай.
3. Инкрементальность. Один логический блок за раз.
4. **Бережное отношение к файлам:** Никогда не удаляй существующие правила, код или конфигурации без явной на то причины. Если нужно изменить файл — дополняй его или заменяй точечно, сохраняя полезный контекст и не ломая соседние блоки.
5. **Формат файлов:** Строго следуй правилам из `PROMPT-copy-paste-files.md` (один файл = один блок, внешний fence из 4 бэктиков для .md, чистый код без лишних слов внутри).
6. **Формат правок файлов (обязательно указывать путь):**
   - **Новый файл:** «Создай `путь/файл.ext`:» + код.
   - **Полная замена:** «`путь/файл.ext` — замени весь файл на это:» + код.
   - **Точечная правка:** ИИ пишет «`путь/файл.ext` — замени:» и выделяет старый код в тройных бэктиках, затем «на:» и новый код в тройных бэктиках (чтобы удобно искать через Ctrl+F).

**Процесс разработки, Git и GitHub:**
7. **Пошаговый Git Flow (Атомарность):** Каждый шаг (Шаг 1, Шаг 2 и т.д.) разрабатывается в отдельной ветке. После завершения шага: (1) обновить `devlog.md` → (2) `git add .` → (3) commit (на английском, многострочные через `-m`) → (4) push → (5) дождаться CI → (6) если красный — чиним в этой же ветке → (7) только после зелёного CI переходим к следующему шагу.
8. **GitHub Issues (Начало дня):** ИИ генерирует Issue для текущего дня. Формат: `[Area] Название (Day N)`. В описании: Контекст, Чек-лист (DoD), Технологии. Метки: `backend`, `frontend`, `infra` и т.д.
9. **Связь PR и Issue:** В описании PR ИИ обязан добавить `Closes #<номер_issue>`.
10. **Коммиты (Conventional Commits):** Строго на английском, без Markdown. Многострочные — через несколько флагов `-m`. Заголовок строго по стандарту: `<type>(<scope>): <description>`.
    - **Типы:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
    - **Scope:** опционально, но желательно (например, `frontend`, `backend`, `api`).
    - **Пример:** `feat(frontend): add calendar page with time scroll`.
11. **Формат PR и Squash-коммита:** При создании PR ИИ предоставляет:
    - Название PR.
    - Описание PR с Markdown-разметкой (для GitHub).
    - Текст коммита для Squash & Merge (чистый текст, без Markdown).
12. **Завершение рабочего дня (Day X):** Перед финальным PR обновить `devlog.md`, `spec.md` (версия + Changelog) и `prompt.md` (план на Day X+1, текущее состояние, уроки).
13. **Безопасность:** Никогда не хардкодь пароли/токены. Используй `.env`. При добавлении новой переменной — обнови `.env.example`.

**Код и Тестирование:**
14. **Sad Path:** При написании тестов обязательно покрывай сценарии с ошибками (404, 401, невалидные данные), а не только успешные.
15. **Навигация по терминалу:** Команды `npm ...` (build, dev, test) выполняются **только** из папки `frontend/`. В начале блока команд ИИ пишет `cd frontend`. Команды `git ...` (add, commit, push) выполняются из **корня** репозитория. ИИ пишет `cd ..` перед коммитом.
16. **Визуальная проверка:** Фронтенд — это UI. Если сомневаешься в верстке/анимациях или хочешь показать результат, ИИ может прямо попросить скриншот/GIF, а ты прикрепишь его в чат. Скриншоты не заменяют CI, но ускоряют проверку визуала.
